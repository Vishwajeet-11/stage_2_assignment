The handler reads the raw body and checks the HMAC-SHA256 signature before it parses JSON. A bad signature is 401 even when the body is not valid JSON. A valid signature with a bad payload is 400. An unknown investor id is 404 and is not queued. The handler returns 200 only after BullMQ accepts the job, and only then stores the Redis claim. It does not wait for the investor update. If enqueue throws, no claim was written, and the handler returns 500.

Redis and Postgres share idempotency. The brief asks for a Redis check and tells the worker to delete that key after success. Deleting the only copy of an event id would make the next delivery look new. The key is written with SET NX and a 24 hour TTL, only after the queue accepts the job. While it exists, a duplicate returns 200 and is not queued. If the process dies before the queue accepts the job, there is no claim, so the retry can still enqueue. The worker updates kyc_status and inserts WebhookEvent in one transaction. It deletes the Redis key only after commit. A later delivery misses Redis, finds the unique event_id, and returns 200. An older timestamp is stored and does not roll kyc_status backward.

WebhookEvent had no investor column. I added investor_id and an index, and left the model name as WebhookEvent. Tenant and Investor are unchanged. The payload has no provider, so the worker stores kyc. Sample ids are not UUIDs, so those fields are non-empty strings. new_status is pending, approved, or rejected.

On GET /investors/:id/kyc-status the tenant and investor come only from a verified HS256 JWT. An unknown id is 404. A tenant or investor mismatch is 403, logged without the token. Stage 1 used 404 for cross-tenant reads. This brief requires 403. last_event_at is the provider timestamp of the newest stored event, the one that decided kyc_status.

The API and worker share a process so startup is two commands. Next I would split the worker, add a dead-letter queue, and store the provider timestamp in its own column.
